日期：2026-10-11（北京时间）。记录定时推送、消息天气摘要及识别会话恢复的修复与验证。

## 现象及已核实证据

- 用户报告正式小程序的预约不报错，但未收到微信消息。
- 主执行从云控制台确认：`hyhqApi` 为 3072 MB / 60 秒，已注册 `hyhqMaintenance` 和 `hyhqWeatherReminders`，已有 `subscribeMessage.send` 权限；没有覆盖包配置的 `HYHQ_WEATHER_REMINDERS_*` 环境变量。
- 云数据库旧预约存在已接受授权、到期仍 `pending` 且 `weather_attempts=0`、`attempts=0` 的记录；另有用户取消的到期预约同样未尝试处理。维护记录最后成功时间仍是 2026-10-07。此证据指向定时入口或工作查询没有执行完成，不能归因为用户未授权、天气 API 返回错误或微信发送接口拒收。
- 本机当前上传目录的压缩包解出后，环境和模板 ID 正确，但提醒目标仍是 `developer`。正式部署改为 `formal`；该参数决定消息打开的小程序版本，单独发现它不能证明无送达的全部根因。
- **13:10 真实触发诊断已确认根因**：微信此次定时事件为小写 `event.Type="timer"`，来源 `TCB_SOURCE="wx_trigger"`、`TRIGGER_SRC="tcb"`，环境匹配且原可信来源判断通过；旧入口只接受大写 `"Timer"`，因此误入普通 API 参数校验并结束，没有执行预约工作。现已在受信任入口兼容 `Timer` 与 `timer`，其他来源、环境、具名触发器和业务开关限制不变。

## cron 与可信定时入口

官方小程序云函数文档要求七字段 cron（秒、分、时、日、月、星期、年），并说明创建 `config.json` 后还需上传触发器。因此原来的 `0 */5 * * * * *` 是每五分钟，不是因多一字段而必然无效。[官方定时触发器说明](https://docs.cloudbase.net/cloud-function/timer-trigger)

按用户新增要求，项目中的调度常量现采用六字段：

- 天气：`0 */5 * * * *`
- 维护：`0 */30 * * * *`

打包入口 `normalizeTimerCron()` 将六字段统一补最后一位年份 `*`，已经包含年份的七字段保持不变。实际云部署仍使用平台支持的七字段，执行频率不变；不以删除已工作的触发器作为试错方式。

原运行入口只认可 `TCB_SOURCE=wx_trigger`。官方环境变量同时记载 `TRIGGER_SRC=timer`，本轮添加该来源的兼容：仅在前者缺失、部署环境完全匹配时接受后者。明确的 `wx_client` 来源不因另一个标记而获得权限，客户端事件里的同名字段不能授予定时权限。[官方环境变量说明](https://docs.cloudbase.net/cloud-function/function-configuration/env)

该来源兼容属于加固，**不是本次已证实的主因**：现场 `wx_trigger` 本来就合法，`TRIGGER_SRC` 实际为 `tcb`；阻断发生在其后的事件类型大小写判断。

## 执行状态与防重发

每次识别为受信任的天气定时调用，会在原管理员专用集合 `hyhq_data` 更新文档 `weather_reminder_state:global`：

- `last_started_at`、`last_finished_at`
- `message_state`：`formal` / `trial` / `developer`
- `status`：`completed` / `disabled` / `failed`
- 成功执行时的汇总 `summary`：`enabled`、`processed`、`sent`、`deferred`、`unknown`、`failed`
- 工作失败只记固定 `error_type=worker_failed`

此文档与新增聚合日志不含 OpenID、账号、预约内容、消息体、提供方原始错误或密钥。无需开通额外日志服务。状态写入失败不会改变已经保存的发送状态，更不会再次请求发送接口。

原有幂等和授权边界保留：已经发送、已取消、已过期及发送回执不确定的记录不会被恢复成待发送；每次主动授权仅对应一次预约；删除账号会撤销尚未进入发送阶段的预约。

### 定时入口最小诊断

在新包尚未观察到工作完成记录时，增加 `weather_timer_diagnostic:global`，仅观测、不授权执行。只接受固定两种触发器名称、`Timer` / `timer` 类型且 SDK 没有用户身份的调用；明确客户端、开发者工具或 HTTP 来源不写入。事务保证每五分钟窗口最多更新一次。

记录只有时间、固定事件类型/名称、经过格式限制的运行时来源标签，以及环境是否存在/匹配、是否通过原可信定时门禁的布尔值。不保存实际环境 ID、任何微信身份、完整事件、正文或密钥。观察到陌生运行时来源仍按原逻辑拒绝工作执行，不能因诊断路径绕过鉴权。

新增回归验证客户端伪造不写入、不执行；陌生无用户定时来源能留下受限诊断但不执行；同窗口不能覆写；下一窗口能记录新的真实运行时来源。

## 独立发送链路复核

| 环节 | 本轮判断 |
| --- | --- |
| 用户授权与收件人 | 前端仅在微信授权结果为 `accept` 时确认；服务端只接受 SDK 获取的微信身份，不信客户端 OpenID。管理员私有收件人绑定与预约一一关联。 |
| 时间 | 服务端接受 5 分钟后到 48 小时内的有时区时间；统一保存 UTC，目标日期与消息显示按 UTC+8；到期后 30 分钟失效。每五分钟检查一次。 |
| 预报 | 工作启动后先将 `weather_attempts` 加一；需要有效且包含预约目标日期的三日预报。失败每五分钟延期，最多五次，最终过期或失败。旧记录的该计数为零，因此尚未到这一环节。 |
| 模板 | 固定使用用户提供的预约提醒模板 8720 对应 ID。字段为 `thing1`、`thing2`、`thing4`、`time26`、`time9`；前三项截断到 20 个字符。 |
| SDK 结果 | 已对照项目锁定的 `wx-server-sdk` 源码：成功返回数值 `errCode:0`，微信失败抛出数值 `errCode`；业务兼容 `errCode` / `errcode`。未发现把标准成功返回误判为失败的问题。 |
| 发送重试 | 明确瞬时拒绝仅有限重试；网络超时或回执不确定进入 `unknown`，不重发。平台错误码仅保存在管理员记录里。 |
| 数据库查询 | 待发查询等值条件 `_kind=weather_reminders,state=…`，按 `scheduled_for` 升序取有界批次。查询异常会中断工作，不会被当作零条。无自定义索引可能慢或触发查询错误，但无现场证据不能断言它必然失败。 |

若现场需要补查询索引，优先核对非唯一复合索引 `_kind + state + scheduled_for`；个人列表则是 `_kind + owner_id + created_at`。维护另用过期/租约/更新时间排序，按实际失败查询补齐，避免一次添加大量无用索引。[官方索引说明](https://docs.cloudbase.net/database/data-index)

## 送达后的追加修复：消息直接显示预约天气

用户收到消息后指出“温馨提示”仍是固定文字。确认原工作器已查询并验证预约城市及目标日期的三日预报，却在组装 `thing4` 时丢弃天气内容。

现改为使用同一次已验证的预报，不增加和风 API 请求：

- `thing2` 保留预约城市；`time26` 保留预约时间。
- `thing4` 显示天气和最低／最高温度，例如 `多云，16～23℃`。
- 根据预约时刻的北京时间选择白天／夜间描述（19:30 至次日 05:59 为夜间）；即使任务延迟跨过边界，也保持预约时刻含义。
- 摄氏温度截断到整数；缺失温度不补零，非摄氏或反转范围不冒充摄氏范围。单个温度缺失时仅展示另一项。
- 字段最长 20 个字符，长描述缩短时保留完整温度；无任何可用天气内容时按原机制延期，不发送空泛文案、不调用订阅发送接口。
- 原来的过期、取消、注销、防重复和发送结果不确定时禁止重发逻辑保持有效。
