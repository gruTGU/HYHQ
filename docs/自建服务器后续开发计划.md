## 3. 第一批：发布与运维基础（S01–S03）

### S01 统一发布自检与环境清单

**已有基础：** `scripts/check.sh`、`scripts/check-miniprogram-compile.mjs`、`check_assessment_runtime`、`scripts/production-smoke.py` 和健康接口。新增工作是把检查结果与发布条件统一起来，不重写这些已验证工具。执行模式必须分开：模型诊断可只读；`check.sh` 会运行独立测试库；`production-smoke.py` 会创建临时用户、图片和真实推理任务，不能在只读预检中自动执行。

- [ ] S01.1 增加只读预检入口，分别输出“通过 / 未通过 / 未核实”，区分必需能力和默认关闭的可选能力；输出机器可读结果及简洁摘要。
- [ ] S01.2 检查代码/迁移版本、模型登记及哈希、部署配置、开发登录关闭、私有目录权限、前端正式 API 地址与域名校验；凭据只报告是否配置。
- [ ] S01.3 将真实微信身份、域名和平台条件列为独立实测项。仅有 AppID/AppSecret 或健康接口 200 不算真实登录通过，模型已登记也不代表 worker 正在运行。
- [ ] S01.4 汇总需人工填写的运营者、联系方式、保留期限及能力依据，生成缺项清单；不推定平台审核通过。

**验收：** 在隔离环境复现缺配置、未迁移、模型不存在和功能关闭，报告能区分并返回约定退出码；执行前后业务数据、队列和预算不变；不外呼供应商、不泄露密钥、连接串或用户正文。必需项失败时不能给出“可发布”结论。

### S02 新版本升级、完整备份恢复与回退

- [ ] S02.1 形成发布清单：Git SHA、依赖、五项 M5 迁移、模型/规则版本、私有文件路径、内容导入及各功能开关。列出代码更新与数据库内容更新的不同步骤。
- [ ] S02.2 用隔离库演练升级；复用现有资料导入和旧文案修正命令，先预览再应用，保留管理员修改，重复执行不得重复入库。
- [ ] S02.3 补齐定期备份方案：PostgreSQL、需保留的私有文件、模型清单及可恢复制品、受限配置；保存机外副本、校验值、保留周期和恢复所需说明。密钥及用户数据不进 Git。
- [ ] S02.4 在独立目录/数据库完整恢复，核对记录关联、私有文件权限、模型可用性及来源；恢复环境默认停止外部调用、任务消费、提醒发送和自动清理，核验后才按需启动。
- [ ] S02.5 写清回退边界：先验证旧代码能否读取新 schema；不能兼容时采用已验证的修复或回退路径。生产已经产生新写入后，不以覆盖旧数据库作为常规代码回退，不回滚已消耗预算、已发送提醒或用户删除/注销状态。
- [ ] S02.6 本地演练通过后，按实际部署安排备份、停止消费者、迁移、更新内容、重启和烟测，核对更新后 SHA。当前规划本身不执行服务器更新。

**验收：** 空环境恢复可复现公开浏览和受控测试身份的识别/私有读取；升级前后原业务内容、关联关系和用量账目一致；新增内容只出现一次；模拟失败可按手册恢复。专门覆盖“升级后新增调用 → 回退/恢复 → 限额仍正确”，包括已发送但结果未知的 LLM 保守占账；隔离测试使用提供方替身。先在工具开发中定义备份一致性策略，避免数据库记录与文件复制时间错位。记录备份覆盖、恢复耗时及尚不能恢复的内容，不能仅以 `pg_dump` 成功验收。

### S03 运行状态、故障定位、保留与告警

- [ ] S03.1 在现有管理端增加受权限保护的运行摘要：当前版本、消费者最近心跳、队列最老等待时间、失败分类、磁盘余量、最近备份/清理结果、天气及 AI 预算。复用现有统计口径和审计，不重复建立业务统计系统。
- [ ] S03.2 补 worker 心跳与异常中断测试；明确“进程存活”和“任务能够前进”的区别。健康检查与后台指标保持轻量，不在公开接口暴露内网路径、用户信息或配置详情。
- [ ] S03.3 配置日志轮转和备份保留工具，补磁盘阈值、队列停滞、服务失败和备份失败的本地告警记录及恢复状态；外部通知渠道后续按实际需要配置，当前不购买或自动发送通知。
- [ ] S03.4 复核已有私有清理 timer；模拟批次先定期生成清理预览与报告，自动删除需单独验证保留规则、确认机制和并发互斥后再纳入启用清单，不能直接绕过现有签名预览。

沿用现有 Admin 权限、统计、审计与任务日志，先实现单机轻量运行状态，不引入 Redis、Celery 或新的监控平台。

**验收：** 隔离环境停止 worker、模拟磁盘不足或备份失败，管理端能显示异常及恢复；普通用户无权读取管理指标；任务不被重复消费，真实观测及受保护批次不被清理；日志不含 Key、原始图片、完整提示词或个人信息。

**第一批交付物：** 预检工具、升级/备份/恢复工具与手册、管理运行摘要、故障回归和脱敏报告。暂不增加新收费服务或新模型供应商。

## 4. 第二批：识别与 AI 的实际质量（S04–S05）

### S04 花卉未知对象与河道实拍评估

- [ ] S04.1 建立有许可的独立样本清单，覆盖五类花卉、范围外花卉、叶片/草地、物品、人像、模糊/暗光、复杂河道和无漂浮物场景；按主体/拍摄序列去重，校准集与最终测试集隔离。
- [ ] S04.2 建立可复用离线评估脚本，报告五类效果、范围外误接收、目标误拒绝、低图质表现及分组样本数。河道另报检测误报/漏报，不能混用花卉指标。
- [ ] S04.3 在校准集评估置信度等拒识策略，查看最终测试结果前固定验收阈值。当前阈值为 0，不直接改成任意常数；不把 softmax 高分当作未知对象识别依据。
- [ ] S04.4 若候选方案有效，再登记为新版本，完善“无法确认 / 重新拍摄 / 查看支持范围”交互和相关科普；历史结果保持原模型及阈值。无效则记录实验并保留现有能力说明，不宣称解决开放类别识别。

**验收：** 保存样本来源、固定划分、可复现指标和失败案例；新旧版本在相同独立测试集比较，原有合法样本退化有明确记录；未知图片不会被文案包装成可靠物种鉴定。朋友仓库模型升级按固定提交/制品单独评估，不自动追随“最新版本”。

### S05 AI 回答、来源、多轮与费用核对

- [ ] S05.1 建立三个板块的固定问题集，包含有资料/无资料、天气新鲜/过期/不可用、未知花卉、空检测、长 Markdown、跨轮指代和资料下架。
- [ ] S05.2 先复用现有离线/模拟回归检查引用、上下文变化和恢复，再在既有预算内做少量真实质量检查；记录调用次数、输入/输出 token 与未确认用量，不提高每日额度来跑测试。
- [ ] S05.3 将“来源是否支持结论、天气时间和地点是否正确、是否杜撰实时监测、是否输出不支持识别结论”作为必查项。引用存在不等于引用支持回答。
- [ ] S05.4 手机长回答、重复点击、切换账户、退出重进与超时重试纳入 S07；优先修复已复现问题，不因质量检查改造成联网搜索或多供应商路由。
- [ ] S05.5 在同一时间窗口核对本项目用量和提供方账单，区分金额、token、缓存计费及账号其他应用用量；取不到金额证据就保留待验。

**验收：** 关键事实与权限/计费问题不得带入启用版本；一般质量问题留样并复测。离线测试、真实回答、真机显示与金额核对分别记录，不能相互替代。
