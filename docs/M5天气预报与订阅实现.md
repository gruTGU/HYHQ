## 1. 对话里的真实天气

入口函数：`weatherdata.context.build_public_weather_context(weather_location_slug, now=None)`。

- 仅接受明确选择的真实 `WeatherLocation.slug`；没有选择、地点停用或不存在时，返回不可用。不会根据示范校园名称、模拟河湖或用户问题猜测城市。
- 严格只读当前地点、当前坐标对应的持久缓存，不调用天气供应商、不预占次数，也不创建缓存行。
- 返回地点范围说明、来源、供应商归因、抓取/失效时间及各项新鲜状态。
- 已过期的天气、空气、预警和预报不向模型提供旧数值，只保留时间、来源和 `stale` 状态。不能把它们写成当前天气。
- 输出可以直接 JSON 序列化。同一缓存有效期内输出稳定，无当前秒数、动态查询时间或不断变化的 age 字段，适合纳入对话上下文修订校验。
- 精度说明仍为附近网格资料，不表示校园内实测；真实天气与示范河湖指标保持独立。

### 模型可用时间边界

这些是本项目对“可作为当前事实”的保守限制，不是上游承诺的更新频率：

- 所有组件都必须有带时区的缓存抓取和到期时间，抓取时间不能晚于当前时间，到期时间必须晚于抓取时间。缺失、倒置或未来抓取时间均返回不可用并移除数值。
- weather / air 的抓取时间达到 3 小时即按过旧处理，即使错误配置了很长的缓存 TTL，也不能继续作为当前天气。上游未提供独立 `observed_at` 时保留 `null`，不能用抓取时间补造观测时间。
- 若 weather / air 明确提供 `observed_at`，必须是带时区的有效时间；达到 3 小时以前的观测置为过期，晚于当前时间 10 分钟以上的观测置为不可用。10 分钟仅用于观测时钟误差容忍，不允许未来的抓取时间。
- 预报逐条要求有效且不重叠的起止时间，单段不超过 36 小时；起点限定在抓取时间前 24 小时至后 72 小时内，以防异常未来区间进入三日预报。已结束区间移除，没有未结束区间时不给模型任何预报值；未来区间仍明确属于预报而非现况。
- alerts 按有效缓存判断，不根据抓取时间伪造预警观测时间。无有效预警组件不等于无预警。
- 以上校验只在固定边界跨越时改变返回状态，无动态秒数、age 或查询时间字段。来源和原缓存时间保留以便核实，异常/过旧组件的 `data` 始终为 `null`。

## 2. 三日天气预报

官方每日预报支持经纬度和 `days` 参数，本项目固定使用 `/weather/v1/daily/{latitude}/{longitude}?lang=zh&days=3`，只展示昼夜天气、最低/最高温度及白天降水概率。规范化保留预报起止时间和完整 `metadata.attributions`。[和风天气每日预报文档](https://dev.qweather.com/docs/api/weather/weather-daily-forecast/)

实现约束：

- 新增 API：`GET /api/v1/weather-data/<slug>/forecast/`。只允许已有活跃地点，不接受任意坐标、天数或额外代理参数。
- 首页原有 `summary/` 仍只有当前天气、空气质量、预警三项；打开首页不额外触发预报。
- 预报使用原有 `WeatherGate`、`WeatherMonth`、`WeatherRequest` 和 `WeatherCache`。出站前预占，失败不退回，与其他天气接口共享月度及近 31 天硬上限；不改变当前更低的部署上限。
- 默认预报缓存 6 小时，服务层将配置约束在 6–24 小时之间。以 5 个地点、每天 4 次估算，约增加 620 次/月；实际请求仍由同一持久账本拦截。请求数量限制不能代替供应商免费权益确认。
- 过期缓存明确显示“历史预报”，已结束的预报时段不在页面展示。缺失概率显示空值标记，0% 不会被误当缺失。
- 白名单仅新增每日天气预报。热带气旋、海洋、辐照仍没有调用入口。

配置（全部由环境变量进入 settings，不写入密钥）：

| 配置 | 默认值 | 作用 |
| --- | --- | --- |
| `QWEATHER_FORECAST_ENABLED` | `0` | 预报总开关 |
| `QWEATHER_FORECAST_ENTITLEMENT_CONFIRMED` | `0` | 已核对专属 Host 对应服务权益 |
| `QWEATHER_FORECAST_TTL_SECONDS` | `21600` | 预报缓存时间 |

命令 `weather_refresh --location <slug> --forecast` 只预览；额外加 `--fetch` 才可能在能力门禁、缓存和原预算允许时请求上游。没有强制绕过缓存或预算的参数。

## 3. 用户如何设置一次提醒

天气页面为 `pages/weather/index`，使用首页已选真实天气地点或入口明确传入的地点，并允许手动切换。

能力核实并开启后，用户流程：

1. 用真实微信账号登录，点击“设置明早提醒”。服务端创建十分钟内有效的准备记录，不等于授权。
2. 页面显示地点、明日北京时间 08:00 及“仅本次”，用户点击“授权这次提醒”。这个点击回调同步调用 `wx.requestSubscribeMessage`，不在页面加载或异步等待后偷偷弹窗。
3. 只有模板对应结果为 `accept` 才保存本次授权。拒绝、关闭、接口不支持或出错不生成发送许可。
4. 授权保存结果不明时可“重试保存授权结果”，复用同一准备记录，不再次弹出授权框；也可以刷新列表核对。
5. 未开始发送的提醒可取消。提醒进入发送中时不能承诺撤回已经发出的请求，接口返回明确状态。

同一用户同一天最多存在一条活跃提醒；更换提醒地点需先取消。重复准备及重复授权确认只返回同一记录。客户端上报不代表微信一定授予可用额度，最终仍以微信发送接口响应为准。

接口：

| 方法与路径（均在 `/api/v1/weather-data/` 下） | 用途 |
| --- | --- |
| `GET reminders/` | 公开开关及当前登录用户自己的近期记录 |
| `POST reminders/intents/` | `{location}` 准备明早一次提醒 |
| `POST reminders/<uuid>/consent/` | `{template_id, acceptance: "accept"}` 确认本次授权 |
| `POST reminders/<uuid>/cancel/` | 取消本人的待发送提醒 |

匿名用户不能创建、确认或取消；其他用户的记录返回 404。响应、操作日志及错误不包含 openid、微信 secret、access token 或上游响应正文。注销用户时对应提醒和发送记录随用户删除。

## 4. 发送、失败与重试

`weather_reminders` 默认只预览候选数；`weather_reminders --send` 才处理发送。每批最多 100 条，默认 50 条。本次没有安装或启用任何定时任务。

- 发送窗口为目标日北京时间 08:00–10:00。worker 只读取该地点、授权时坐标、目标日且尚未过期的预报缓存，不请求和风天气。
- 缓存缺失或过期时等待下一次检查，不消费消息许可、不补发旧天气、不突破天气预算；到 10:00 仍不可用则过期。
- 许可状态先持久化为发送中，另一 worker 不会重复发送。成功后永久转为已发送。
- 获取 token 前的网络失败、微信明确返回系统繁忙或 token 失效可以有限重试，最多 3 次发送尝试，间隔 5/10 分钟并受发送窗口限制。
- 消息提交后发生超时、非正常响应或进程中断，可能已经发出；转为“发送结果待核实”，不自动重发。微信接口没有本项目可依赖的消息幂等键，因此不承诺跨网络故障的严格 exactly-once。
- 微信明确拒绝授权、模板/页面错误及未识别错误停止发送；不试图绕过用户许可。
- 用户停用、地点停用/坐标变更、模板或字段配置变化均阻止旧许可继续发送。
- 关键准备、授权、取消、发送和结果写入既有审计表；单次投递另存尝试序号、时间和安全错误代码。管理后台只读查看，不提供手工增加授权次数或任意重发入口。
- 消息天气文字附“和风天气”，落地预报页完整展示供应商归因。实际模板容量及消息展示是否满足来源条款需核对后才能开启能力门禁。
